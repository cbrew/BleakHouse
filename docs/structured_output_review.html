Structured Output Capability Review

Evidence-based review of structured-output behaviour across five model/provider combinations. Each cell below was produced by a single isolated probe call; raw responses are linked from each cell. All probes run 2026-05-13.

Executive summary — top empirical findings

  1. No two providers share the same JSON Schema subset. Every test in groups B–C reveals at least one provider/model that diverges from the others, even on features the JSON Schema spec considers basic.
  2. Anthropic Haiku rejects the most schema features outright. It returns HTTP 400 on maxItems, minItems > 1, uniqueItems, minimum/maximum, additionalProperties: true. Notably it accepts maxLength at the API layer but does not enforce it at decode time (emitted a 66-char string for maxLength=10). That asymmetry — accept-but-ignore — is the trap.
  3. DeepInfra's vLLM rejects uniqueItems with HTTP 500 ("Grammar error: Unimplemented keys"), except for one model (Qwen3-Next) on which the API accepts it but the decoder silently doesn't enforce it. Same hosting, different per-model behaviour.
  4. OpenAI strict=true can produce non-JSON output when prompt and schema are in irreconcilable conflict. The minItems=2 test with a prompt demanding 1 item produced 1024 tokens of garbled alternating tokens — neither schema-valid nor parseable. The strict flag eliminates "wrong field types" surprises but introduces "cornered decoder" surprises.
  5. The list-loop pathology is universal. Given an unbounded list[Literal] schema and a prompt demanding 50 repeats, every model emits the requested duplicates up to the token budget. Only providers/models that accept maxItems can prevent the pathology at decode time. (See test 12.)
  6. Strict-mode comparison on OpenAI-compatible providers (test 14) shows that strict=false degrades constraint honoring on most candidates while strict=true enforces, except where strict-mode-specific errors block the call entirely.
  7. Sanity-tier features work everywhere: enum, nullable (anyOf null), minLength, pattern, format:date — all five candidates honor these.
  8. Output truncation at very low max_tokens (test 15) is uniform: all candidates emit partial JSON that fails to parse. There is no graceful "I had to truncate" signal in the response body itself — only finish_reason=length in the usage object.
  9. gpt-oss-120B has the cleanest schema-feature profile in this matrix — passes every feature tested except uniqueItems (accepted-but-not-honored, same posture as Qwen) and minLength on a conflicting prompt. Even minItems=2 and additionalProperties=true work where competitors fail.
  10. Both gpt-oss models leak reasoning_content on DeepInfra (140 / 110 chars even on a trivial "output 'ok'" prompt). The thinking text doesn't appear in choices[0].message.content but is billed as output tokens. Callers reading only content see clean structured output and a surprising token count. Fully manageable via extra_body={"reasoning_effort": "low"} — see the supplementary probe in the gpt-oss takeaway section, which shows the parameter is honoured by DeepInfra and cuts output tokens by ~60% on realistic prompts.
  11. gpt-oss models obey loop prompts cleanly (50 items for "50 times"), where Qwen3-Next overshot to 170+ on the same prompt. The Qwen failure mode is unique to that model on this hosting.
  12. Same model, different hosting, materially different behaviour. gpt-oss-120B was probed on both DeepInfra and Together. Together hides reasoning_content entirely (no thinking leak) — a clear win for callers reading just content — but Together's grammar engine is worse on conflict-with-prompt cases: maxItems, minItems>1, and the strict-mode test all produced JSON-invalid output on Together where DeepInfra honoured them cleanly. Hosting is a real schema-capability axis; the model identity is not enough to predict behaviour.

Addendum 2026-05-17 — Gemma 4 26B-A4B-it repetition pathology under grammar-constrained decoding

Findings recorded during the Tier L listener-prep work for BleakHouse-dll8 (short-prose generation panel). The single-shot 16-test probe matrix at the top of this document does not surface this failure mode because it tests very short outputs against synthetic schemas; the bug only appears at production prompt/schema scale (multi-turn segment-script prompt, full Segment Pydantic schema, ~600-word target). This addendum is what ruled gemma-4-26B-A4B-it out of the listener panel.

  1. Failure mode: repetition loop under JSON-schema decoding. Gemma 4 26B-A4B-it on DeepInfra, called with the multi-turn segment-script prompt and the full Segment output schema, produces grammar-valid prefixes that then degenerate into pure-whitespace loops (then mixed-whitespace loops under mitigation attempts) until the output budget exhausts. finish_reason ends up length, output fails Pydantic validation. The loops are inside what the grammar admits as valid string contents.
  2. Root cause is upstream, not BleakHouse-side. Tracked as vLLM issue #40080; fix is open PR #40099 (auto-enable RepetitionDetectionParams under structured-output decoding). PR has been open and not merged at DeepInfra as of 2026-05-17. The bug is a Gemma 4 × xgrammar interaction — cross-confirmed by external reports on Vertex, Cloudflare, ollama, and llama.cpp under structured output. Plain (non-grammar) decoding on the same model and prompt is fine. This is a structured-output-specific pathology, which is exactly why it belongs in this document.
  3. Empirical fail rate at default sampler: 2/5 first-try schema-valid for the BH seg-0 opening prompt; smoke valid (single trivial probe) + benchmark fail + 3 retries (2 valid + 1 fail). Other seg indices (1–4) were 5/5 first-try valid for the same model. The pathology concentrates on the opening-segment prompt shape, presumably because the opening directive frees up the most token budget for whitespace before any structural anchor is hit.
  4. Mitigations attempted and failed. Three independent BleakHouse-side mitigations were probed; none helped, two regressed:
    • list_field_caps={"emphasis_words": 3} — no improvement. The schema already self-caps the field at 2 items; the cap was redundant and not where the loop forms.
    • Simpler opening directive in the prompt — no improvement. The loop is decode-time, not prompt-time.
    • frequency_penalty=0.3 + stop=["\n×5"] + extra_body.repetition_detection — worse: 0/5 valid. frequency_penalty pushed pure-newline loops into mixed-whitespace loops the stop string can't catch; the extra_body hint is silently ignored by DeepInfra's current vLLM (no error, no behaviour change).
    Forensic artefacts kept under data/eval/stage2_tier_l_prose/gemma-4-26b-a4b/: .degenerate.json, .retry{1,2,3}.json, list_caps_probe/, simpler_opening_probe/, rep_mitigations_probe/.
  5. Disposition for Tier L: ruled OUT of the dll8 listener panel. 5/5 canonical samples do exist (seg-0 was promoted from retry-2) but production routing can't accept the ~30% retry overhead on openings, and the model is uniquely bad here — its 31B-dense sibling (gemma-4-31B-it) has no such pathology and finished second in the eventual Tier L listener panel (57% win-rate, BleakHouse-kl4f.6, 2026-05-17).
  6. Generalisable lesson for this document. Single-shot probe matrices like the test 1–16 grid at the top of this page are systematically optimistic for grammar-constrained decoding pathologies. They use small prompts, small schemas, and short generations — none of which give the decoder enough rope to enter a stable repetition basin. Production-shaped probes (real prompts, real schemas, real output budgets) are required to catch this class of bug. We should consider adding a "production-shaped smoke" tier to the methodology before promoting any new open-weight model to a routing decision.
  7. Re-probe trigger: when DeepInfra ships a vLLM release that includes PR #40099 (or its successor) and RepetitionDetectionParams are enabled by default under structured output, re-run the dll8 panel for this model. Until then the cost table entry stays as-is; routing for short-prose stays on the sibling 31B-dense or one of the other listener-eligible candidates (qwen3-235b-a22b-2507 was the listener winner at 60%).

Bd tracking: diagnosis lives in BleakHouse-dll8 notes; the model-level disposition is captured in memory as project_gemma4_repetition_bug.

Addendum 2026-05-18 — Two-tier schema strategy for the host_prep cluster

Findings and design decisions for the host_prep Phase 2.5 cluster: PreInterviewResponse, HostQuestion, HostBrief in enrichment/podcast_types.py. Driven by a real empirical asymmetry observed against the same call sites under different providers, this addendum is what the codebase now does and why.

The empirical asymmetry

Same prompts, same schemas, two providers, opposite failure modes:

  • Anthropic Claude Sonnet 4.6 on the host_prep_brief task: produces 5 questions per segment whether the prompt asked for "3–5" or "3–4", and emits 10–15 proposed_references per interview when the registry holds >20 tags (Anthropic over-proposes; the entire downstream listener_pick winnow stage exists to cut 60+ raw refs down to ~6 recommended).
  • Qwen3-235B-A22B-Instruct-2507 on DeepInfra, same prompts: emits empty lists when the schema permits and the prompt is even slightly hedged. 8 of 9 interviews emitted proposed_references=[]; 2 of 3 brief calls emitted zero questions before min_length was added (observed 2026-05-17 in scripts/probe_host_prep_qwen_vs_anthropic.py).

The implication: a schema that's correct for one model is wrong for the other. The host_prep prompts were tuned to Anthropic over time; Qwen needed different governance.

The design

The Pydantic models in enrichment/podcast_types.py are the single source of truth for the strict schema. All list fields in PreInterviewResponse / HostQuestion / HostBrief carry min_length=1, max_length=4; HostBrief.questions is special-cased to min_length=3, max_length=4 (a 1-question brief isn't a podcast segment). All three models also carry model_config = ConfigDict(extra='forbid') for additionalProperties: false.

Two paths through the seam apply the schema differently:

Path A — Qwen on DeepInfra (and openai-compatible hostings generally)

The full Pydantic-generated schema, complete with minItems / maxItems / additionalProperties: false, is sent to the provider verbatim. Qwen's vLLM-backed decoder enforces all three at decode time. Valid output is produced by construction. The seam does no schema transformation on the way out and no coercion on the way back.

Path B — Anthropic messages.create()

Anthropic's output_config rejects minItems, maxItems, and several other JSON Schema features (verified 2026-05-13: HTTP 400 with "For 'array' type, property 'maxItems' is not supported"; verified 2026-05-17: "For 'object' type, 'additionalProperties' must be explicitly set to false"). The seam's Anthropic provider therefore does two things:

  1. On the way out: _denature_schema_for_anthropic() reduces the schema to an allowlist of keys we know Anthropic accepts. The allowlist is type, properties, required, items, $ref, $defs, additionalProperties, enum, anyOf, const, description, format, default, title. A separate set of known-rejected keys (minItems, maxItems, uniqueItems, length / numeric bounds, pattern, multipleOf) get their values folded into the parent's description as natural-language notes ("Maximum 4 items. Minimum 3 items."). Anything else is dropped silently — if a future Pydantic version emits a new keyword we haven't catalogued, it doesn't leak through.
  2. On the way back: the response goes through Pydantic model_validate_json, which fires the @field_validator(mode='before') coercers defined on each host_prep model. The coercers pad lists shorter than min_length with placeholder values (string "[unspecified]" for list[str]; a HostQuestion-shaped dict for HostBrief.questions), truncate lists longer than max_length to the cap, and log the coercion at INFO so the diagnostic isn't silently lost.

Allowlist design (rather than denylist)

The original strip helper used a denylist of known-rejected keys. The 2026-05-18 refactor switched to an allowlist for two reasons: (1) new Anthropic restrictions land as a stripped-key rather than a 400 — the seam keeps running, the caller gets a coerced response; (2) Pydantic versions that emit new keywords (JSON Schema 2020-12 etc.) don't accidentally leak through. The known-rejected list still exists, but only to source the description-note text — its job is now annotation, not gate.

Why coercion lives on the Pydantic model (not in the Anthropic provider)

The constraint and the coercion sit in the same file. A reader can answer "what happens if Anthropic returns an empty list" without crossing module boundaries. The trade-off: the validator also fires for Qwen-side responses, which should never violate. When the coercion no-ops (because the input is already valid) it's free; if Qwen ever does produce a violation, the INFO log line is the diagnostic.

What this lets us do, what it doesn't

  • Lets us keep one set of Pydantic models across providers. No HostBriefStrict / HostBriefLoose duplication. No per-provider Pydantic configs.
  • Lets the Qwen path stay structurally enforced while the Anthropic path is structurally permissive + post-hoc coerced. Both arrive at the same validated state.
  • Doesn't help with anything Anthropic doesn't strip but does enforce loosely — e.g. if Anthropic returns a string where an integer is expected, the strict-validation error propagates. The coercion only handles list-length violations because those are the ones Anthropic's schema subset can't constrain in the first place. Wrong-type / wrong-enum violations would still raise.
  • Doesn't apply outside the host_prep cluster. Other Pydantic models in podcast_types.py (SegmentTemplate, EpisodeSegment, Turn, Utterance, …) don't yet carry list-length constraints or before-validator coercers. Extending them is tracked in BleakHouse-vyo4 (migrate all production Pydantic models to extra='forbid', remove seam-side schema mutation).

Per-model takeaways

Anthropic Haiku 4.5

  • API-rejected at request time: maxItems, minItems > 1 (only 0/1 allowed), uniqueItems, minimum/maximum, additionalProperties: true, schemas where const-only properties lack a type.
  • Accept-but-ignore (the trap): maxLength on strings is accepted at the API layer but not enforced at decode time. Watch for this when porting from another provider.
  • Honored at decode time: enum, nullable, const (when type is present), minLength, pattern, format:date. Always strict-mode equivalent — no strict flag.
  • Practical pattern: use the SDK's messages.parse() (Pydantic-aware) which auto-transforms unsupported schema features into description text, or strip them yourself before calling messages.create(). Both this codebase (anthropic_provider._strip_unsupported_schema_keys) and the SDK's parse() take the second / first approach respectively.

OpenAI gpt-4o-mini

  • Strict mode is reliably enforcing on the constraints it accepts. Test 14 (maxItems test side-by-side strict on/off) shows the strict flag actually does work as advertised.
  • Strict mode is also fragile: conflicting prompt+schema (test 05 minItems=2 + "give me 1") produced 1024 tokens of garbled non-JSON. The decoder couldn't satisfy the schema and produce coherent text simultaneously. Better to detect prompt/schema conflicts before sending.
  • API-rejected: uniqueItems, additionalProperties: true (strict mode requires every object to have additionalProperties: false), schemas missing type on a property.
  • Honored: maxItems, minItems (any value), maxLength, minLength, pattern, minimum/maximum, format strings, const (with type), enum, nullable.
  • Cache reporting: usage.prompt_tokens_details.cached_tokens (authoritative; populated automatically for prompts ≥ 1024 tokens with a shared prefix).

DeepSeek V4-Flash on DeepInfra

  • API-rejected: uniqueItems (HTTP 500: "Grammar error: Unimplemented keys"). Everything else in our test set accepted.
  • Honored: maxItems, minItems, maxLength, minLength, pattern, minimum/maximum, format:date, const, enum, nullable, additionalProperties:true.
  • Cache reporting: usage.prompt_tokens_details.cached_tokens is populated by DeepInfra for this model. Plus usage.estimated_cost (DeepInfra extension) ships an authoritative per-call bill — prefer this over recomputation.
  • Pathology: unbounded list[Literal] loops (test 12) — but only when no maxItems is set. With maxItems present (test 04), the decoder clips cleanly.
  • License: MIT. Multi-provider hostable.

Gemma 4 26B-A4B-it on DeepInfra

  • API behaviour identical to DeepSeek on this hosting on most tests (rejects only uniqueItems). Confirms most schema-feature acceptance is a vLLM/DeepInfra-side decision, not a model-side one.
  • At chapter scale (from this session's separate eval, not this probe) Gemma collapsed to 53% schema validity — short-input probes are systematically more optimistic than chapter-scale runs.
  • Repetition-loop pathology under grammar-constrained decoding at production prompt/schema scale: ruled this model OUT of the Tier L listener panel (2026-05-17). Root cause is vLLM #40080 / open PR #40099, not BleakHouse-side. See the 2026-05-17 addendum above for the full diagnosis, failed mitigation attempts, and re-probe trigger.
  • No estimated_cost in the response for this model — DeepInfra only ships it on some models.

gpt-oss-120B / gpt-oss-20B on DeepInfra

  • Schema-feature behaviour at this hosting: see the matrix above — both probed on the same 16 tests as the other open-weight candidates.
  • Multi-provider footprint is by far the widest in this review — 22 providers for the 120B, 11 for the 20B. This makes them the lowest-lock-in choice if portability matters more than per-provider quirks.
  • Hyperscaler coverage (Azure, AWS Bedrock, Google Vertex, Cloudflare) is a meaningful operational point: if your organisation already has an enterprise relationship with one, gpt-oss may be the only open-weight model in this review you can route through that contract.

Methodology


For each (candidate, test) pair we make one request, with these conventions:


    
  
  • Anthropic Haiku: client.messages.create(...) with output_config={"format": {"type": "json_schema", "schema": ...}}. We deliberately do not pre-strip unsupported features — we want to observe what the API rejects.
    • 
  
  • OpenAI-compatible: client.chat.completions.create(...) with response_format={"type": "json_schema", "json_schema": {"name": ..., "schema": ..., "strict": ...}}. Default strict=true except where a test compares both modes.
    • 
  
  • Tokens, finish_reason, cache_read_tokens, and (where the provider ships it) usage.estimated_cost are captured from the authoritative response.
    • 
  
  • Schema compliance is verified independently with the jsonschema library (Draft 2020-12). The "specific compliance" verdict applies a per-test predicate (e.g. for maxItems=2, does the parsed list actually have ≤2 items?). These can disagree when the API accepted the schema but the decoder didn't enforce the constraint.
    • 
  
  • Raw results cached under data/eval/structured_output_review/<candidate>__<test_id>.json so the script is resumable.
    •
