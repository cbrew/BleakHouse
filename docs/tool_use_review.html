Tool-use review across providers

Empirical review of tool-use semantics across Anthropic messages.create, OpenAI Responses API (POST /v1/responses), and OpenAI Chat Completions (POST /v1/chat/completions). Goal: ground the BleakHouse seam's tool-use abstraction in observed behaviour rather than guessed shapes. Sourced from a mixture of vendor docs (fetched 2026-05-15) and one-call pilots against gpt-5-mini and the patterns in enrichment/host_prep.py for Anthropic. This document underpins docs/provider_control_spec.md Subtask C; it is the "C1 survey" deliverable referenced from BleakHouse-n60y.

1. Why these three APIs

BleakHouse host_prep currently runs an agentic tool loop against Anthropic Haiku (messages.create(tools=ALL_TOOLS)). When the --provider-profile all_openai path lands (BleakHouse-otae Subtask D), that loop has to run against OpenAI too. OpenAI exposes two distinct surfaces:

  • Responses API (/v1/responses) — the current recommended surface for gpt-5 family. Has separate reasoning + visible output items. The OpenAI parallel pipeline already uses this for Phase 3 prose.
  • Chat Completions (/v1/chat/completions) — the legacy surface, still supported by gpt-5 family and the way openai-compat providers (DeepInfra, Together, Cerebras) expose function calling.

The seam needs to support both OpenAI shapes since openai-compat hostings don't all implement Responses. Anthropic is its own thing.

2. Three conventions side by side

2.1 Tool spec format

Anthropic OpenAI Responses OpenAI Chat Completions 
{
  "name": "get_weather",
  "description": "...",
  "input_schema": {
    "type": "object",
    "properties": {"city": {"type":"string"}},
    "required": ["city"]
  }
}
 
{
  "type": "function",
  "name": "get_weather",
  "description": "...",
  "parameters": {
    "type": "object",
    "properties": {"city": {"type":"string"}},
    "required": ["city"],
    "additionalProperties": false
  }
}
 
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "...",
    "parameters": {
      "type": "object",
      "properties": {"city": {"type":"string"}},
      "required": ["city"]
    }
  }
}

Three different shapes for the same idea:

  • Anthropic uses input_schema; OpenAI both use parameters.
  • Responses API flattens function fields (name/description at the top level next to type: "function"); Chat Completions nests them under function.
  • Anthropic doesn't use a wrapping type field — tools are always "functions".

2.2 How tool calls appear in the response

Anthropic OpenAI Responses OpenAI Chat Completions

In response.content, blocks with type == "tool_use":

{
  "type": "tool_use",
  "id": "toolu_01abc...",
  "name": "get_weather",
  "input": {"city": "Paris"}
}

Loop signal: response.stop_reason == "tool_use".

input is a parsed dict.

In response.output, items with type == "function_call":

{
  "type": "function_call",
  "id": "fc_0dbe...",
  "call_id": "call_uwie...",
  "name": "get_weather",
  "arguments": "{\"city\":\"Paris\"}"
}

Loop signal: presence of any function_call items (or absence of message items with output_text).

arguments is a JSON string; caller must json.loads it.

The item has BOTH id (fc_...) and call_id (call_...) — distinct values. Tool results route by call_id.

In choices[0].message.tool_calls:

{
  "id": "call_abc...",
  "type": "function",
  "function": {
    "name": "get_weather",
    "arguments": "{\"city\":\"Paris\"}"
  }
}

Loop signal: finish_reason == "tool_calls".

arguments is a JSON string.

2.3 How tool results are returned for the next turn

Anthropic OpenAI Responses OpenAI Chat Completions

Append two messages to messages:

[
  ...prior messages...,
  {"role":"assistant",
   "content": response.content},   // echo back the assistant turn
  {"role":"user",
   "content":[
     {"type":"tool_result",
      "tool_use_id":"toolu_01abc...",
      "content":"Temperature: 25C"}
   ]}
]

Multiple tool_result blocks may appear in one user message — that's how parallel calls are answered.

Append items to the input list. Critical: echo the function_call back (along with any paired reasoning item) before the output:

[
  ...prior input...,
  <reasoning item from prior turn>,
  <function_call item from prior turn>,
  {"type":"function_call_output",
   "call_id":"call_uwie...",
   "output":"Temperature: 25C"}
]

Match on call_id (NOT the function_call's top-level id).

Append a role: "tool" message per call:

[
  ...prior messages...,
  {"role":"assistant",
   "tool_calls":[ <the original tool_calls> ]},
  {"role":"tool",
   "tool_call_id":"call_abc...",
   "content":"Temperature: 25C"}
]

Match on tool_call_id.

3. Empirical surprises

Surprise 1 — gpt-5 family function_calls must be echoed WITH their paired reasoning item

Documented behaviour says "append the function_call_output for each call you handle and re-send the input". Empirically, gpt-5-mini rejects the next turn with HTTP 400 if you echo the function_call item back without ALSO including the reasoning item that immediately preceded it in the prior response: 

openai.BadRequestError: Error code: 400 — {'error': {'message':
  "Item 'fc_0dbe...' of type 'function_call' was provided without
   its required 'reasoning' item: 'rs_0dbe...'."}}

Pragmatic fix: pass all output items from the prior turn back into input, in order, before appending the function_call_output. The seam should do this transparently; callers shouldn't have to know about reasoning items.

Pilot: /tmp/pilot_responses_tool_use.py, 2026-05-15, gpt-5-mini.

Surprise 2 — arguments are a JSON string in both OpenAI APIs but a parsed dict in Anthropic

Anthropic's SDK pre-parses tool_use.input into a Python dict. Both OpenAI APIs hand back arguments as a JSON-encoded string; callers must json.loads. The seam should normalise to dict so the executor sees the same shape regardless of provider.

Surprise 3 — three different identifier conventions

Anthropic uses tool_use.id (single field), matched on tool_use_id in the result. OpenAI Responses uses two ids: id (fc_...) is the item id and call_id (call_...) is what tool results route by. OpenAI Chat Completions has one field id (call_...) that doubles as the tool_call_id for results.

The seam should expose one identifier per call (the "result routing key") to the caller and bury the provider-specific id juggling.

Surprise 4 — parallel-call semantics differ by default

Anthropic and OpenAI Chat Completions both allow multiple tool_use / tool_calls in one response by default; the caller iterates them and returns matching result blocks. Responses API mirrors this — response.output can contain multiple function_call items in one turn. The parallel_tool_calls request flag (default true) gates this on the OpenAI side. The Anthropic loop in host_prep.run_pre_interview_with_tools already handles parallelism by iterating all tool_use blocks in response.content — the seam should do the same.

Surprise 5 — loop-termination signals are all different

Anthropic: stop_reason goes from "tool_use" back to "end_turn" when done.
OpenAI Responses: no explicit flag; check for absence of function_call items (or presence of a message item with text output).
OpenAI Chat Completions: finish_reason == "stop" (vs "tool_calls" when more work is queued).

The seam abstracts these into one rule: "loop until no tool calls remain in the latest response".

4. Implications for the BleakHouse seam (Subtask C design notes)

Translated from this survey into concrete decisions for enrichment/llm/:

ConcernDecision
ToolSpec shape One provider-neutral dataclass: name, description, input_schema (JSON Schema dict, matches Anthropic's existing key). Providers translate to their wire format.
Tool executor Caller passes a dict[str, Callable[[dict], str]] mapping tool name → executor. The seam loops and dispatches; callers don't see the per-provider transcript shape.
Arguments Seam normalises to a parsed dict before calling the executor; OpenAI's JSON-string is parsed inside the provider, not by the executor.
Identifier Seam exposes one call_id per call (whatever the provider's "results route by" key is). Anthropic's tool_use.id and OpenAI's call_id map to it.
Transcript The seam returns a tool_transcript: list[ToolCall] for audit. Each entry has name, input (dict), output (str), iteration number.
Max iterations Default 6, configurable per request — matches the existing host_prep MAX_TOOL_CALLS.
Echo-back state Hidden inside the provider implementation. For Responses, this means transparently echoing prior reasoning + function_call items. For Anthropic, echoing the prior assistant message. Callers see only "request in, final response + transcript out".
Reasoning items (Responses) Cached transparently; not exposed to caller; not counted as caller-visible output text.

5. Open questions deferred to C3/C4

  • Tool-result error reporting: when the executor raises, should the seam (a) bubble the exception, (b) inject a "tool error: ..." string as the result and let the model recover, or (c) both? Anthropic's tool_result blocks have an is_error flag; OpenAI's function_call_output doesn't. Pick a convention.
  • The strict flag on individual function definitions (OpenAI). Today's pilots run without it; some tools may benefit. Decide whether to expose it on ToolSpec.
  • For openai-compat hostings (DeepInfra, Together, Cerebras) — do they honour the same Chat Completions tool-calling shape? structured_output_review.html already shows hosting-level divergence on json_schema; tool-use parity needs a parallel survey before we declare full coverage. Track separately.
