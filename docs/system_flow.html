BleakHouse system flow

Function-focused walk through the pipeline: every component that touches data on the way from raw novel text to a hosted audio episode, LLM and non-LLM alike. The focus is "what role does this play in the system," not provider/cost detail (those are covered in docs/structured_output_review.html, docs/together_batch_assessment.md, docs/self_hosted_provider_assessment.md).

Models shown are the production default profile (Anthropic). Every LLM stage below routes through the provider-control seam (enrichment/llm/); the active provider profile decides which model serves each task. Switching to --provider-profile all_openai replaces Haiku with gpt-5-mini and Sonnet with gpt-5.4 across the pipeline, and individual tasks can be overridden via --provider-override TASK=MODEL_ID. See docs/provider_control_spec.md for the full task inventory and the "Provider control" section below for a summary.

Stage-by-stage detail

StageComponentFunction in systemInputs → OutputsLLM?
Novel ingest curl from Gutenberg, then enrichment/segment_novel.py Pulls the source HTML, splits it into chapters and then into paragraph-level "passages" with stable IDs (c5:p17). Hand-coded per-novel logic for boundary detection (chapter headings vary across editors); for modernist novels without chapters, splits on paragraph count with explicit start/end markers. Gutenberg HTML → passages_raw.json (list of {passage_id, chapter_id, chapter_title, paragraph_index, char_start, char_end, text}) —
Per-paragraph literary enrichment enrichment/submit_passages_enriched.py + collect_passages_enriched.py (Anthropic Batch API, Haiku 4.5, per-chapter call shape). OpenAI parallel: enrichment/submit_passages_enriched_openai.py + collect_passages_enriched_openai.py (OpenAI Batch via Responses API endpoint, gpt-5-mini, per-chapter with paragraph chunking). Tags every paragraph with the literary features the downstream selection optimizer needs. One call per chapter (or chapter-chunk for the OpenAI path) returns a FieldReportEnrichment per paragraph: interest score 0-5, named characters present and speaking, narrator type, plot function, emotional register, theme tags, quotability, accessibility, summary, best-quote, plus seven "provision dimensions" (character development / plot advancement / thematic depth / social critique / humor / atmosphere / narrative technique). These provision scores are the substrate that Phase 1's optimal-transport solver matches against each expert's per-dimension demand vector. The OpenAI variant writes to passages_enriched.openai_5_mini.json alongside the default file; --enrichment-variant openai_5_mini on run_pipeline.py selects it. Both Batch paths are native (50% discount) and bypass the seam — see "Carve-outs" below. passages_raw.json → passages_enriched.json (Anthropic) or passages_enriched.openai_5_mini.json (OpenAI) yes — default Haiku 4.5 batch; OpenAI gpt-5-mini batch as alternative
Per-paragraph situating context enrichment/submit_passage_contexts.py + collect_passage_contexts.py. Anthropic Batch API, Haiku 4.5, per-paragraph call shape, whole chapter as cached prompt prefix. Implements Anthropic's "Contextual Retrieval": writes a one-sentence situating paragraph that grounds each passage in its chapter (who's present, where we are, what just happened). The output prose is concatenated with the raw passage text before being embedded by LanceDB in the embedding-variant pipeline. Without this, a passage like "two figures floated on the Thames" doesn't retrieve under a "Gaffer Hexam fishing for corpses" query because the proper names appear only in the surrounding text. The whole-chapter prompt prefix is shared across the N per-paragraph calls and recovered at Anthropic's cache_read rate. passages_enriched.json + raw chapter text → passages_contextual.json (per-paragraph context field added) yes — Haiku 4.5 batch, ~60k+ calls total, uses prompt caching
Passage clustering enrichment/cluster_literary.py (HDBSCAN over enrichment provision dimensions), enrichment/cluster_characters.py (graph clustering over per-paragraph character co-occurrence) Groups passages that are similar along literary axes or that share a recurring character set. Used by Phase 1 as supplementary structure (passages within a cluster are interchangeable for some segment-template slots) and by the webapp for "similar passages" displays. passages_enriched.json → clusters_literary.json, clusters_characters.json —
Vector indexing (embedding variant only) enrichment/embed_passages.py + LanceDB. Reads passages_contextual.json; concatenates context + text + characters + themes + summary for each passage and embeds with OpenAI text-embedding-3-small via LanceDB's embedding registry. Provides cosine-similarity retrieval for the --pipeline embedding variant of Phase 1+2. The other two pipelines (transport and no-passages) don't use vectors at all. This is the only live OpenAI usage in the system, and it's not chat-completion — it's embeddings via the LanceDB adapter. passages_contextual.json → LanceDB table on disk OpenAI embeddings (not chat completion) — only in embedding variant
Phase 0: episode-segment design enrichment/design_segments.py via run_pipeline.py::run_phase0. Routes through the seam (task design_segments); structured output via Pydantic JSON Schema. Decides the episode's high-level shape. Given the expert panel and arc demands for the run, the model proposes 3–7 segment templates (name, segment_type, min/max passage count). These are not tied to specific passages yet — they're the skeleton that Phase 1's matcher fills in. The model is essentially performing literary instructional design: balancing pace, depth, contrast, and persona coverage across the episode. experts + arc demands → phase0_segments.json (list of SegmentTemplate) yes — default Haiku 4.5 (one call per run); gpt-5-mini under all_openai
Phase 1+2: passage matching and ordering — transport variant enrichment/transport_podcast.py + enrichment/segment_transport.py. Sinkhorn / optimal-transport solver from OR-tools. Hard combinatorial optimization, no model in the loop. Treats segment-template demands and per-passage provision scores as supply and demand on a bipartite graph, then solves for the assignment that minimizes unmet demand subject to segment min/max passage caps. The result is a deterministic, reproducible mapping: each passage either gets a segment or doesn't, and the ordering within segments is fixed by demand-weight + chronological order in the source novel. passages_enriched.json + phase0_segments.json + expert/arc demands → phase1_assignments.json, phase2_plan.json —
Phase 1+2 — embedding variant enrichment/embedding_podcast.py. LanceDB cosine search. Alternative matcher: queries the LanceDB table built upstream with text formed from each expert's persona + segment template; picks top-K passages by cosine similarity. Useful for runs where the "shape" of an expert is better captured semantically than by the provision-dimension vector. LanceDB table + phase0_segments.json → same output filenames OpenAI embeddings (query side) — see vector indexing row
Phase 1+2 — no-passages variant run_pipeline.py::run_phases_1_2_no_passages Skips passage grounding entirely. The episode template is preserved, but each segment carries an empty assignments list. Phase 3's prompt will tell the model to "speak from memory" about the topic. Used as a baseline / ablation to test how much the literary-features grounding actually buys at the script level. same input → same output schema, empty assignments lists —
Phase 2.5a: pre-interview (per expert × per segment) enrichment/host_prep.py::run_pre_interview_with_tools. Routes through the seam (task host_prep_pre_interview) with an agentic tool loop up to 6 calls (search OpenAlex / search Wikipedia / read Wikipedia article); a second seam call (task host_prep_pre_interview_structured) extracts the structured response. Generates the expert's private prep notes. The host doesn't see this output directly; it feeds Phase 2.5c. Each expert is told their persona and the segment's passages, and is allowed to look up scholarly references through tools. The output is a PreInterviewResponse: key points the expert wants to make, potential quotes from sources, points of disagreement they might raise. The tool-loop shape is unusual in this pipeline (everything else is single-turn): it lets the expert ground claims in actual citations rather than only in the model's training data. The seam abstracts provider-specific tool-call shapes — see docs/tool_use_review.html. persona + segment passages → conversation transcript → structured PreInterviewResponse (saved into phase2_5_interviews.json) + CitationRegistry yes — default Haiku 4.5 with Anthropic tool-use; gpt-5-mini with OpenAI Chat-Completions tool-calling under all_openai. Only when --host-prep.
Phase 2.5b: reading-list winnowing enrichment/host_prep.py::_select_listener_recommendations via the seam (task listener_pick). Free-text JSON parsed by regex with a fall-back-to-all-candidates safety net. Curates the listener-facing "for further reading" list. The agentic interview loop accumulates a registry of references (every [ref-N] tagged result from the tool calls), often 20-50 candidates per (expert × segment). This call drops it to a 3-5 item list a general podcast listener would actually pursue: accessible books, not specialist journals, not paywalled. The cut is editorial — selecting which references make it to the published reading list, not generating new ones. candidate reference list + segment context → 3-5 selected refs yes — default Haiku 4.5; gpt-5-mini under all_openai. Only when --host-prep.
Phase 2.5c: host brief (per segment) enrichment/host_prep.py::plan_questions via the seam (task host_prep_brief); structured output to HostBrief. Synthesizes the host's question plan for the segment. Reads all the experts' pre-interview responses for this segment and produces a HostBrief: steering notes, anticipated questions (each tagged to a target expert and intent), cross-engagement opportunities (where one expert's claim might prompt another to push back). This is what Phase 3 sees alongside the passages — the host's "show prep document" for that segment. pre-interview responses for one segment → one HostBrief yes — default Sonnet 4.6; gpt-5.4 under all_openai. Only when --host-prep.
Phase 3: script generation (per segment) enrichment/generate_podcast.py::generate_segment_script via the seam (task generate_podcast); structured output to EpisodeSegment. Alt driver: enrichment/phase3_runner.py for cerebras / gpt-5.4 via Responses API (bypasses the seam for separate reasoning + output budgets). Writes the actual dialogue. Each call gets: the segment's persona descriptions, its assigned passages with full text, optional host brief, segment context (previous/next titles, first/last flag). The model emits a list of Turn objects, each with a speaker, text, and per-utterance TTS annotations (pause_before_ms, rate, quote_mode, emphasis_words). These annotations are what the audio stage will consume — the script generation step is responsible for them as a creative choice (e.g. "the host should pause for emphasis here"). segment plan + passages + (optional) host brief + personas → list of EpisodeSegment with Turns → phase3_episode.json yes — default Sonnet 4.6 (one call per segment); gpt-5.4 under all_openai, or via the alt driver with Responses API.
Phase 4a: report + manifest enrichment/post_phase3.py, webapp/build_manifest.py, webapp/build_report.py. Builds the human-readable artifacts: a plain-text report of the run, an HTML report for browsing, and a manifest.json that's the source of truth for which segments / turns / passages exist (used by the webapp's experiment-tracker view). Reads only the existing JSON artifacts; emits new files. phase3_episode.json + run config → report.txt, report.html, manifest.json —
Phase 4b: quote verification enrichment/precompute_quote_verification.py. One Haiku call per quoted passage. Defends against hallucinated quotes. Phase 3 sometimes attributes lines to characters that don't actually appear in the source. This step extracts every quoted passage from phase3_episode.json and asks the model to verify, against the actual source text, whether the quote appears verbatim. Results stored as quote_verification.json and surfaced by the webapp so a reader can see "verified" / "paraphrased" / "not in source" badges next to each quote. phase3_episode.json + source passages → quote_verification.json yes — Haiku 4.5, one call per quoted passage
Phase 4c: TTS rendering (per turn) enrichment/render_audio.py + enrichment/tts_profiles/classic.py. Gemini 2.5 Flash TTS by default, 3.1 Flash TTS for the alternative trevelyan_v2 profile. Synthesises one audio shard per turn. The prompt builder turns each turn's structured representation into a TTS prompt with voice direction blocks (speaker / accent / energy / style) and per-utterance prosody hints (rate, quote-mode, emphasis). Each speaker maps to a prebuilt Gemini voice via params.yaml:speakers.voices. Output is per-utterance PCM, glued together with the pause_before_ms silences from Phase 3. phase3_episode.json → per-turn PCM → per-shard MP3 (192 kbps) + audio/shards.json (one entry per shard with content-addressed md5) Gemini TTS
Audio storage cas/store.py (Content-Addressed Store). Local layer hashes bytes into data/cas/files/md5/<prefix>/<rest>; R2 layer mirrors them to Cloudflare R2 via boto3. The audio bytes never live in the source tree. Each shard is identified by its md5; the same shard rendered twice (e.g. two runs that produced identical text+voice+model) deduplicates automatically. audio/shards.json stores only the md5 + per-shard metadata; webapp uses cas.store.url(md5) to construct an R2 URL when serving. MP3 bytes → data/cas/... (local) and R2 (remote); shards.json carries md5s —
Database build scripts/build_content_db.py. SQLite (data/content.db). Snapshots the per-run JSON artifacts (manifest, phase outputs, character arcs, etc.) into a queryable database for the webapp. Stores raw JSON bytes verbatim so round-trips are byte-identical; the trust contract is "the JSON in the DB is the same JSON that lived under data/runs/." Re-built after any new run lands. data/runs/*/*.json + data/novels/*/character_arcs.json → data/content.db —
Webapp serving webapp/app.py (legacy live site) and webapp_v2/app.py (newer, cleaner reimplementation in progress). FastAPI + Jinja templates. Serves the experiment tracker (matrix of which novel × panel × strategy has been rendered), the listen pages (per-episode transcript with seekable utterances), and the audio itself (302-redirects to R2 URLs constructed via cas.store.url(md5) — webapp doesn't carry R2 credentials, only the public URL pattern). All reads from data/content.db; no direct filesystem reads at request time. content.db + R2 URLs → HTML pages + audio redirects —

What each LLM role does for the system

The previous table covers where the calls happen. This section steps back to summarise why there are LLM calls at all — what each role is doing for the architecture. The names below are the production-default models; under --provider-profile all_openai the same roles are filled by gpt-5-mini (Haiku tier) and gpt-5.4 (Sonnet tier). The functional split is the architecture; the choice of model behind each role is configuration.

Haiku 4.5 (or gpt-5-mini) — the structural workhorse

Haiku appears in five distinct functional roles:

  1. Producing the substrate for Phase 1's optimizer (per-paragraph enrichment). The transport solver needs a vector of provision scores per passage; Haiku is what creates those vectors. Without enrichment, the matching stage has nothing to match on.
  2. Producing situating prose for retrieval (passage contexts). A paragraph is often referentially under-specified in isolation; Haiku writes the chapter-level "where we are" sentence that gets prepended before embedding. Anthropic's contextual-retrieval pattern; not a structured-output task, just free prose.
  3. Proposing the episode skeleton (Phase 0 segment design). Given the panel of experts and the arc demands, propose 3-7 segments. This is the only Haiku call where the output drives episode-level structure, not paragraph-level metadata.
  4. Running scholarly tool-loops for the host's prep (Phase 2.5 pre-interview). The expert "speaks" in a 6-turn agentic loop with search tools; Haiku is the conversation policy. This is the only LLM call in the whole system that's allowed to fetch external information at run-time.
  5. Editorial curation (reading-list winnow, quote verification). Two small tasks where the model is asked to pick or check rather than generate. Both are guarded — if the model picks badly or fails to verify, the system still produces an episode; it just has a less polished reading list or unmarked quotes.

The unifying property: Haiku is used wherever the cost-per-quality trade favours small structured outputs. Volume is high (hundreds of thousands of per-paragraph calls across the corpus); per-call output is small. The pipeline doesn't ask Haiku to write anything a listener will hear.

Sonnet 4.6 (or gpt-5.4) — the writer

Sonnet is reserved for the calls whose output is consumed by a human listener (directly or via TTS):

  1. Host brief synthesis (Phase 2.5c) — the question plan the host will follow. Read by the script generator, not by listeners, but its quality directly shapes script quality.
  2. Script generation (Phase 3) — the dialogue itself. One call per segment, structured output to a Turn list with per-utterance TTS annotations. The annotations matter as much as the words: pause_before_ms values are creative choices the model makes about timing.

The unifying property: Sonnet is used where the output is read aloud or shapes what's read aloud. Volume is low (a few segments per run); per-call output is large (~10-50k tokens of dialogue + structure).

Gemini TTS — the voice

Single role: synthesise the audio. Per-turn calls, voice mapped from params.yaml, prosody annotations from the Phase 3 output baked into the prompt. No text generation, no decision-making.

OpenAI embeddings — the original silent dependency, no longer silent

The --pipeline embedding variant of Phase 1+2 uses text-embedding-3-small via LanceDB's embedding-registry adapter (the other two pipeline variants don't need it). What's changed: OPENAI_API_KEY in the env no longer exists only for embeddings. The all_openai provider profile sends every LLM stage of the active pipeline through OpenAI's Chat Completions and Responses APIs; the embedding adapter is now just one of many OpenAI consumers in the system.

Provider control

Every interactive LLM call in the active pipeline routes through enrichment.llm.generate(GenerationRequest(task=..., ...)). The seam resolves task to a ModelSpec via enrichment.llm.settings, which reads its routing table from params.yaml:

  • task_models — base layer mapping each task to a default generator (e.g. passage_enrichment: anthropic_haiku_4_5).
  • provider_profiles — named overrides. production uses the base layer; all_anthropic is an alias; all_openai overrides every task to gpt-5-mini or gpt-5.4.
  • default_provider_profile — what runs when --provider-profile is omitted.

CLI surface on run_pipeline.py:

--provider-profile NAME          # default from params.yaml
--provider-override TASK=ID      # repeatable; layers on top of the profile

Example: an all-OpenAI run with one task pinned to Anthropic Sonnet:

--provider-profile all_openai \
--provider-override host_prep_brief=anthropic_sonnet_4_6

Each run's config.json records a providers block: {profile, overrides_at_runtime, resolved_per_task, enforced_by_call_sites}. resolved_per_task is the source of truth: a complete task → generator-id map of what actually ran. enforced_by_call_sites: true means every call site honoured the resolution; if a carve-out is added in the future it must flip this to false.

Carve-outs

Three stages bypass the seam by design:

  • Native batch enrichment (submit_passages_enriched.py / submit_passages_enriched_openai.py + submit_passage_contexts.py): use Anthropic Batch and OpenAI Batch directly for the 50% native-batch discount. Provider choice surfaces through the variant-file convention (passages_enriched.openai_5_mini.json) and the --enrichment-variant CLI flag. Consolidating these under a seam-native batch surface is tracked as a deferable follow-up.
  • Alt Phase 3 driver (enrichment/phase3_runner.py): drives gpt-5.4 via the Responses API directly so reasoning and visible output have separate token budgets — a gpt-5-family feature the seam's Chat Completions path doesn't expose. The in-pipeline generate_podcast task still routes through the seam.
  • Embedding-pipeline curate call (enrichment/embedding_podcast.py): pipeline-conditional (only runs under --pipeline embedding); migration tracked separately and deprioritised since the OT alternatives comparison runs on transport.

What's not in this picture

  • No LLM evaluation in the production loop. The structured-output review (docs/structured_output_review.html) and the cost/portability assessments are all experimental — they live in scripts/ and don't run on production data, only on probe fixtures.
  • No LLM in Phase 4a (report/manifest). Reports and manifests are templated from existing artifacts; quote verification is a separate phase that does call the LLM.
  • No streaming. Every LLM call in the system is request/response (or batch + poll for the two batch endpoints). No SSE, no token streaming, no progressive UI.
  • No retrieval-augmented generation at script time. Phase 3 sees the actual passage text in its prompt; it doesn't query the LanceDB index. The vector index exists only for Phase 1+2 matching in the embedding variant.
  • No fine-tunes. Every model is used in its stock form, prompted via system messages and structured-output schemas.
