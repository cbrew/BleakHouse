BleakHouse system flow

Novel to audio, function-focused — every component that touches data on the way from raw novel text to a hosted audio episode, LLM and non-LLM alike.

The pipeline is built around a single provider-neutral seam. Each LLM stage names the task it performs; the active profile in params.yaml chooses which provider and model fills that task for a given run. Anthropic and OpenAI are equal first-class providers — there is no implicit default below the named profile.

All provider-routing happens through enrichment/llm/. CLI surface on run_pipeline.py: --provider-profile NAME picks a named profile; --provider-override TASK=GENERATOR_ID layers per-task overrides on top. The two reference profiles ship out of the box: all_anthropic (Haiku 4.5 + Sonnet 4.6) and all_openai (gpt-5-mini + gpt-5.4). Mixed profiles are a config edit.

Stage-by-stage detail

StageComponentFunction in the systemInputs → Outputs
Novel ingest curl from Project Gutenberg, then enrichment/segment_novel.py Pulls the source HTML, splits it into chapters and then into paragraph-level "passages" with stable IDs (c5:p17). Per-novel boundary detection is hand-coded — chapter headings vary across editors; for modernist novels without chapters, splits on paragraph count with explicit start/end markers. Gutenberg HTML → passages_raw.json
Per-paragraph enrichment Anthropic side: submit_passages_enriched.py + collect_passages_enriched.py. OpenAI side: submit_passages_enriched_openai.py + collect_passages_enriched_openai.py. Both use the native batch API for the 50% discount. Tags every paragraph with the literary features the downstream optimizer needs. One call per chapter (chunked for OpenAI) returns a FieldReportEnrichment per paragraph: interest score 0-5, characters present and speaking, narrator type, plot function, emotional register, theme tags, quotability, accessibility, summary, best-quote, plus seven provision dimensions (character development / plot advancement / thematic depth / social critique / humor / atmosphere / narrative technique). These provision scores are the substrate Phase 1's optimal-transport solver matches against per-dimension demand. passages_raw.json → passages_enriched.json (Anthropic-derived) or passages_enriched.openai_5_mini.json (OpenAI-derived). --enrichment-variant on run_pipeline.py selects which file a run reads.
Situating context submit_passage_contexts.py + collect_passage_contexts.py. Native batch. Whole-chapter prompt cached across the N per-paragraph calls. Anthropic's "contextual retrieval" pattern: writes a one-sentence situating paragraph that grounds each passage in its chapter (who's present, where we are, what just happened). Concatenated with the raw passage before embedding. Without it, a passage like "two figures floated on the Thames" doesn't retrieve under a "Gaffer Hexam fishing for corpses" query because the proper names live only in the surrounding text. passages_enriched.json + raw chapter text → passages_contextual.json
Passage clustering cluster_literary.py (HDBSCAN), cluster_characters.py (graph clustering) Groups passages similar along literary axes or sharing a recurring character set. Used by Phase 1 as supplementary structure (interchangeable slots) and by the webapp for "similar passages" displays. passages_enriched.json → clusters_*.json
Vector index (embedding variant only) embed_passages.py + LanceDB. OpenAI text-embedding-3-small via LanceDB's embedding registry. Provides cosine-similarity retrieval for the --pipeline embedding variant of Phase 1+2. The other two pipeline variants (transport, no-passages) don't use it. passages_contextual.json → LanceDB table on disk
Phase 0 · segment design design_segments.py via run_pipeline.py::run_phase0. Seam task design_segments; structured output to SegmentDesignResult. Decides the episode's high-level shape. Given the expert panel and arc demands, the model proposes 3–7 segment templates (name, segment_type, min/max passage count). Not yet tied to specific passages — the skeleton that Phase 1's matcher fills in. The model is performing literary instructional design: balancing pace, depth, contrast, persona coverage. experts + arc demands → phase0_segments.json
Phase 1 + 2 · transport variant transport_podcast.py + segment_transport.py. Sinkhorn / optimal-transport solver from OR-tools. Hard combinatorial optimization, no model in the loop. Treats segment-template demand and per-passage provision as supply on a bipartite graph; solves for the assignment that minimises unmet demand subject to segment min/max caps. Deterministic and reproducible. passages_enriched.json + phase0_segments.json → phase1_assignments.json, phase2_plan.json
Phase 1 + 2 · embedding variant embedding_podcast.py. LanceDB cosine search. Alternative matcher: queries the LanceDB table with text formed from each expert's persona + segment template; picks top-K by cosine similarity. Useful where the "shape" of an expert is better captured semantically than by the provision-dimension vector. LanceDB + phase0_segments.json → same output filenames
Phase 1 + 2 · no-passages variant run_pipeline.py::run_phases_1_2_no_passages Skips passage grounding entirely. Template preserved; each segment carries an empty assignments list. Phase 3's prompt tells the model to "speak from memory" about the topic. Used as a baseline / ablation. same schema, empty assignments
Phase 2.5a · pre-interview host_prep.py::run_pre_interview_with_tools. Two-phase: seam task host_prep_pre_interview with tools (agentic loop) → seam task host_prep_pre_interview_structured (no tools) extracts the structured response. Per expert × per segment, generates the expert's private prep notes. The host doesn't see this output directly; it feeds the brief. Each expert is told their persona and the segment's passages and may look up scholarly references through search_openalex / search_wikipedia / read_wikipedia_article (up to six tool turns). The two-phase pattern keeps the loop free-form and the extraction structured. Tool-call shapes are normalised by the seam — see docs/tool_use_review.html. persona + segment passages → PreInterviewResponse + CitationRegistry → phase2_5_interviews.json
Phase 2.5b · reading-list winnow host_prep.py::_select_listener_recommendations. Seam task listener_pick. Free-text JSON parsed by regex, with a fall-back-to-all-candidates safety net. Editorial curation. The interview loop accumulates a registry of references (every [ref-N]-tagged result from the tool calls), often 20–50 candidates per (expert × segment). This call drops it to 3–5 a general podcast listener would actually pursue: accessible books, not specialist journals, not paywalled. Picks not generates. candidate list + segment context → recommended[] subset of phase2_5_reading_list.json
Phase 2.5c · host brief host_prep.py::plan_questions. Seam task host_prep_brief; structured output to HostBrief. Synthesises the host's question plan per segment from all experts' pre-interview responses. Steering notes, anticipated questions (each tagged to a target expert and intent), cross-engagement opportunities. Read by Phase 3 alongside the passages — the host's "show prep document". pre-interview responses → one HostBrief → phase2_5_host_briefs.json
Phase 3 · script generation generate_podcast.py::generate_segment_script. Seam task generate_podcast; structured output to EpisodeSegment. Alt driver phase3_runner.py uses the Responses API directly for gpt-5-family separate reasoning + output budgets. Writes the actual dialogue. Each call gets the segment's persona descriptions, assigned passages with full text, optional host brief, segment context (previous / next titles, first / last flag). The model emits Turn objects with speaker, text, and per-utterance TTS annotations (pause_before_ms, rate, quote_mode, emphasis_words). The annotations matter as much as the words — they're the creative-control surface for the audio stage. plan + passages + brief + personas → EpisodeSegment per segment → phase3_episode.json
Phase 4a · report + manifest post_phase3.py, webapp/build_manifest.py, webapp/build_report.py Templated rendering: plain-text report, HTML report, manifest.json (source of truth for the webapp's experiment tracker). Reads existing JSONs only. phase3_episode.json + run config → report.txt, report.html, manifest.json
Phase 4b · quote verification precompute_quote_verification.py. Seam task quote_verification; one call per quoted passage. Defends against hallucinated quotes. Phase 3 occasionally attributes lines to characters that don't appear in the source. This step extracts every quoted passage from phase3_episode.json and asks the model to verify against the actual source text. Results surfaced as "verified" / "paraphrased" / "not in source" badges in the webapp. phase3_episode.json + source passages → quote_verification.json
Phase 4c · audio render render_audio.py + tts_profiles/classic.py. Gemini 2.5 Flash TTS by default; 3.1 Flash TTS for the trevelyan_v2 profile. One audio shard per turn. The prompt builder turns each turn's structured representation into a TTS prompt with voice direction blocks (speaker / accent / energy / style) and per-utterance prosody hints. Speaker→voice mapping comes from params.yaml:speakers.voices. Output is per-utterance PCM stitched with the pause_before_ms silences from Phase 3. phase3_episode.json → per-shard MP3 (192 kbps) + audio/shards.json (md5-keyed)
Audio storage cas/store.py. Local layer hashes bytes into data/cas/files/md5/<prefix>/<rest>; R2 layer mirrors via boto3. Audio bytes never live in the source tree. Each shard is identified by its md5; identical shards across runs (same text + voice + model) deduplicate automatically. audio/shards.json stores only the md5 + per-shard metadata; the webapp constructs R2 URLs via cas.store.url(md5). MP3 bytes → data/cas/… (local) + R2 (remote)
Database build scripts/build_content_db.py. SQLite (data/content.db). Snapshots every run's JSON artifacts into a queryable DB for the webapp. Stores raw JSON bytes verbatim; the trust contract is "the JSON in the DB is the same JSON that lived under data/runs/". Re-built after any new run lands. data/runs/*/*.json + data/novels/*/character_arcs.json → data/content.db
Webapp webapp/app.py (live) and webapp_v2/app.py (clean-room rewrite). FastAPI + Jinja. Serves the experiment tracker, the per-episode listen pages, and 302-redirects to R2 audio URLs. All reads from content.db; no direct filesystem reads at request time. Webapp does not carry R2 credentials — it only constructs URLs. content.db + R2 URLs → HTML + audio redirects

Two model tiers, two providers

The pipeline distinguishes two functional model tiers, regardless of provider. Each tier is filled by a different model in each profile:

Small-model tier — the structural workhorse

Haiku 4.5 · gpt-5-mini

High call volume, small per-call output, low cost. Used for:

  • Per-paragraph enrichment — produces the substrate for Phase 1's optimizer.
  • Situating context — chapter-level grounding sentences for retrieval.
  • Phase 0 segment design — proposes 3–7 segments per run.
  • Pre-interview tool loops — agentic search + summarise per expert × segment.
  • Editorial picks — reading-list winnow and quote verification.

None of this tier's output is read directly by a listener.

Large-model tier — the writer

Sonnet 4.6 · gpt-5.4

Low call volume, large per-call output, higher cost. Used for:

  • Host brief (Phase 2.5c) — the question plan the script generator follows.
  • Script generation (Phase 3) — the dialogue, with per-utterance TTS annotations that shape what the listener hears.

Output is either read aloud by the TTS stage or directly shapes what is.

The split is architectural; the choice of model that fills each role is configuration. --provider-profile all_anthropic and --provider-profile all_openai are the two reference profiles. Mixed profiles (Anthropic enrichment + OpenAI prose, or vice versa) are a config edit in params.yaml.

Other models in the system

  • Gemini 2.5 Flash TTS (and the trevelyan_v2 3.1 Flash variant) — synthesises the audio. Per-turn calls; voice mapping from params.yaml; no text generation.
  • OpenAI text-embedding-3-small — only in the --pipeline embedding variant, only for vector retrieval, accessed via LanceDB's embedding registry rather than a chat-completions client.

Provider control

Every interactive LLM call in the active pipeline routes through enrichment.llm.generate(GenerationRequest(task=..., …)). The seam resolves task to a ModelSpec via enrichment.llm.settings, which reads its routing table from params.yaml:

  • task_models — the base layer: a generator id per task.
  • provider_profiles — named overrides on the base layer. Empty profile body = "use task_models as-is".
  • default_provider_profile — what runs when --provider-profile is omitted.

CLI surface on run_pipeline.py:

--provider-profile NAME          # default from params.yaml
--provider-override TASK=ID      # repeatable; layers on top of the profile

Example — all-OpenAI run, but pin the brief planner to Sonnet so the host's reasoning gets the Anthropic prose tier specifically:

--provider-profile all_openai \
--provider-override host_prep_brief=anthropic_sonnet_4_6

Each run's config.json records a providers block: {profile, overrides_at_runtime, resolved_per_task, enforced_by_call_sites}. resolved_per_task is the source of truth — a complete map of what actually ran for each task. enforced_by_call_sites: true means every call site honoured the resolution; if a future carve-out doesn't, it must flip this to false.

Carve-outs

Three stages bypass the seam by design:

  • Native batch enrichment (per-paragraph enrichment, passage contexts): uses Anthropic Batch and OpenAI Batch directly for the 50% native-batch discount. Provider choice surfaces through the variant-file convention (passages_enriched.openai_5_mini.json) and the --enrichment-variant CLI flag.
  • Alt Phase 3 driver (enrichment/phase3_runner.py): drives gpt-5.4 via the Responses API directly so reasoning and visible output have separate token budgets. The in-pipeline generate_podcast task still routes through the seam.
  • Embedding-pipeline curate call (enrichment/embedding_podcast.py): pipeline-conditional (only under --pipeline embedding); migration tracked separately.

What's not in this picture

  • No LLM evaluation in the production loop. The structured-output review and cost / portability assessments are experimental — they live in scripts/ and run only on probe fixtures.
  • No streaming. Every interactive LLM call is request / response; batch endpoints are submit + poll. No SSE, no token streaming, no progressive UI.
  • No retrieval-augmented generation at script time. Phase 3 sees the actual passage text in its prompt; it does not query the LanceDB index. The vector index exists only for Phase 1+2 matching in the embedding variant.
  • No fine-tunes. Every model is used in its stock form, prompted via system messages and JSON Schema response formats.
  • No LLM in report / manifest. Quote verification is its own phase; reports and manifests are templated from existing artifacts.
