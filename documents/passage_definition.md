# What Is a "Passage" in the Enrichment Pipeline?

## The Problem

The beads tasks (`bh-6xw`, `bh-76m`, `bh-bcz`, etc.) all refer to "passages" as the
unit that gets enriched, that experts express preferences over, and that gets matched
to program needs. But "passage" is ambiguous. This document pins down what it means,
what granularity options exist, and how the choice connects to the existing codebase.

## What the Codebase Currently Has

The download pipeline (`bleak_house/download.py`) produces **chapters** as the
primary unit. Each chapter is a dict:

```python
{
    "id": "c1",                          # Gutenberg anchor ID
    "book_title": "Bleak House | Project Gutenberg",
    "title": "In Chancery",             # Chapter title
    "text": "London. Michaelmas term..."  # Full chapter text, paragraphs joined
}
```

There are 67 chapters (plus preface and front matter), stored as a flat JSON list.
Chapter text is plain text with `\n`-separated paragraphs, extracted from Gutenberg
HTML via lxml xpath. No sentence segmentation. No sub-chapter structure.

The LLM enrichment step (`notes_prompt.py`) sends each chapter's full text to an LLM
and gets back a `ChapterSchema`: a list of `LiteraryElement` objects (KeyMoments,
ThemesAndAnalysis, CharacterHighlight, etc.). Each element has free-text analysis
fields and a `Quotes: list[str]` field containing verbatim text from the chapter.

The existing pipeline produces **621 LiteraryElement objects** across 69 chapters
(~9 per chapter on average).

## Three Candidate Definitions of "Passage"

### Option 1: Passage = LiteraryElement (current output unit)

A passage is one `LiteraryElement` from the existing `ChapterSchema` output. This is
what the LLM already produces: a unit of analysis paired with supporting quotes.

```
Chapter "In Chancery"
  -> LiteraryElement[0]: KeyMoments("The chapter exposes the inefficiency...")
  -> LiteraryElement[1]: ThemesAndAnalysis("Major themes include...")
  -> LiteraryElement[2]: CharacterHighlight("The Judge", "The judge is...")
  ...
```

**Identity**: `(chapter_id, element_index)` e.g. `("c1", 3)`

**What it looks like as a passage**:
- Summary/Discussion/Analysis text (1-3 sentences of expert-generated commentary)
- Supporting quotes from the original text
- Already typed by literary function (theme, character, style, etc.)

**Advantages**:
- Already exists -- 621 of them, with quotes
- Natural unit for expert preferences: "I want to discuss this character insight"
- Already carries a literary function type (KeyMoments, ThemesAndAnalysis, etc.)
  which maps naturally to provision dimensions
- Right granularity for a podcast segment (one talking point)

**Disadvantages**:
- Generated by LLM, not by the text itself -- coverage depends on prompt quality
- Not anchored to specific text spans (quotes are included but offsets aren't tracked)
- May miss material the LLM didn't find interesting on first pass
- Different LLM runs produce different elements from the same chapter

### Option 2: Passage = Paragraph (raw text unit)

A passage is a paragraph from the original Gutenberg text, split on `\n` boundaries.

**Identity**: `(chapter_id, paragraph_index)` e.g. `("c1", 7)`

**What it looks like**:
- A block of Dickens' prose, typically 3-10 sentences
- No analysis attached -- raw source material

**Advantages**:
- Stable and deterministic -- same text every time
- Complete coverage -- nothing is missed
- Anchored to specific text positions

**Disadvantages**:
- Too granular for expert preferences (hundreds of paragraphs per chapter)
- No literary analysis attached -- would need enrichment from scratch
- Many paragraphs are connective tissue, not independently interesting
- Paragraph boundaries in Gutenberg text don't always match meaningful units

### Option 3: Passage = Enriched Text Span (new unit, synthesized)

A passage is a contiguous span of chapter text (one or more paragraphs) that has been
identified as a coherent unit of literary interest, then enriched with provision
dimensions. This is what the legal pipeline's "sentence enrichment" stage produces,
adapted for literary content.

```python
class Passage(BaseModel):
    passage_id: str              # e.g. "c1:p3-5"
    chapter_id: str              # "c1"
    chapter_title: str           # "In Chancery"
    text: str                    # The actual Dickens prose (1-3 paragraphs)
    char_start: int              # Offset into chapter text
    char_end: int                # Offset into chapter text
    quotes: list[str]            # Key quotable lines within the span
    provisions: Provisions       # 7-dimension enrichment
    contribution_role: ContributionRole  # INTRODUCES, DEVELOPS, etc.
    literary_element_type: str   # "character", "theme", "plot", "style", etc.
    summary: str                 # 1-2 sentence description of what this passage does
```

**Identity**: `(chapter_id, char_start, char_end)` -- anchored to text positions

**Advantages**:
- Grounded in actual text, not just LLM commentary
- Carries both the source material AND its enrichment
- Experts can react to the text itself, not just to a summary
- Spans can overlap (a paragraph about Lady Dedlock is both character and plot)
- Deterministic text anchoring enables reconstruction and citation

**Disadvantages**:
- Requires a new segmentation + enrichment step (more LLM calls)
- Boundary decisions are non-trivial (where does one passage end and another begin?)
- More complex data model

## Recommended Approach: Hybrid (Option 1 grounded by Option 3)

Use the existing `LiteraryElement` outputs (Option 1) but **anchor each one to its
source text span** (Option 3). This means:

1. **Keep the existing enrichment pipeline** -- `ChapterSchema` with its list of
   `LiteraryElement` objects. These are the "expert observations."

2. **Add text grounding** -- for each `LiteraryElement`, identify which paragraph(s)
   in the chapter it refers to, using the `Quotes` field to locate the span. Store
   `char_start` / `char_end` offsets.

3. **Add provision dimensions** -- enrich each grounded `LiteraryElement` with the
   7 provision dimensions and contribution role. This can be done in the same LLM
   call that produces the element, or as a second pass.

4. **Define "Passage"** as the combination:

```python
class Passage(BaseModel):
    # Identity
    passage_id: str                # "c1:elem3"
    chapter_id: str                # "c1"
    chapter_title: str             # "In Chancery"

    # Source text grounding
    text_span: str                 # The Dickens prose this element refers to
    char_start: int                # Offset in chapter
    char_end: int                  # Offset in chapter
    quotes: list[str]             # Verbatim quotes (from existing Quotes field)

    # Literary analysis (from existing LiteraryElement)
    element_type: str              # "KeyMoments", "CharacterHighlight", etc.
    analysis: str                  # The Summary/Discussion/Analysis text
    character_name: str | None     # If CharacterHighlight

    # Enrichment (new)
    provisions: Provisions         # 7 literary dimensions
    contribution_role: ContributionRole  # INTRODUCES, DEVELOPS, CULMINATES, etc.
    strategic_value: int           # 0-5: how interesting for a podcast
```

This gives us a unit that:
- An **expert** can browse and say "yes, I want to talk about this"
- A **producer** can see provision coverage for
- The **match matrix** can score against program needs
- Is **traceable** back to the actual novel text

## How This Connects to Each Beads Task

| Task | How it uses Passage |
|------|-------------------|
| `bh-6xw` Chapter Enrichment | Produces Passages by enriching LiteraryElements with provisions + text grounding |
| `bh-76m` Expert Profiles | Experts express affinity for Passages based on provisions and element_type |
| `bh-62a` Program Structure | Segments declare needs; Passages are candidates to fill them |
| `bh-bcz` Match Matrix | Scores Passage provisions against Segment needs, filtered by expert affinity |
| `bh-e2x` Gap Detection | Identifies Segments with insufficient Passage coverage |
| `bh-ci5` Producer Brief | Shows top Passages per segment, with provenance back to chapter text |

## Quantity Estimates

- 67 chapters, ~9 LiteraryElements each = ~600 Passages
- After text grounding, some elements may merge (same span, different angles) or
  split (one element spanning disconnected text)
- Expected final count: 500-700 Passages
- This is a manageable size for expert browsing and match matrix computation
